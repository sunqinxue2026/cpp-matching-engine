## 3. 已实现的功能

基准程序通过公开的 `MatchingEngine` 接口运行三类负载：

1. `submit_non_crossing`：提交非交叉买单，规模1000、10000、100000。
2. `cancel_active_orders`：先建立相同规模的活动买单，再在计时区间逐笔撤销。
3. `match_one_trade_per_order`：在计时区间逐对提交一张被动卖单和一张主动买单，每次产生一条成交；规模按成交对计数。

每类记录：

- 总操作数。
- 总耗时毫秒。
- 单操作纳秒数。
- 每秒操作数。
- 校验用checksum。

输出包含编译器宏版本、C++标准、硬件并发线程数、使用的时钟以及计时区间说明。程序会检查拒单、最终活动订单数和成交数量；结果不符合预期时退出失败。

## 4. 运行过的命令和测试结果

目标环境为本机Windows、Zig 0.13.0 / Clang 18.1.6、CMake 4.4.4、Ninja、C++17 Release。基准使用 `std::chrono::steady_clock`，避免系统时间调整影响测量。硬件型号、CPU频率和内存大小应以实际运行机器记录为准；程序只自动记录 `hardware_concurrency()`，不把它当作完整硬件描述。

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DMATCHING_BUILD_BENCHMARKS=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
./build/performance_benchmark --output benchmark_results.csv
```

基准输出的 `benchmark_results.csv` 应保存到构建或报告目录，不要提交到GitHub。首次运行时应记录完整命令、编译器、构建类型、操作系统和是否启用优化；不要混合Debug与Release数字。

本轮实际验证命令为：

```sh
cmake -S . -B <临时构建目录> -G Ninja -DCMAKE_BUILD_TYPE=Release -DMATCHING_BUILD_BENCHMARKS=ON -DMATCHING_BUILD_GTEST=OFF
```

## 5. 核心数据结构、算法和公式

生产撮合仍使用价格有序的 `std::map`、同价 `std::list` FIFO和订单ID位置哈希索引；基准不复制这些结构，也不使用参考模型。基准只通过 `MatchingEngine::submitOrder()` 和 `cancelOrder()` 触发真实逻辑。

计时定义：

\[
ns/op = \frac{milliseconds \times 1{,}000{,}000}{operations}
\]

\[
ops/s = \frac{operations}{milliseconds/1000}
\]

提交负载不交叉，避免将撮合成本混入提交指标。撤单负载把建簿放在计时区间外，单独测量撤单。撮合负载在计时区间内交替提交一张卖单和一张可交叉买单，以避免“先堆积大量对手单再逐笔调用深度快照”造成平方级极端负载；每个操作对产生一条成交。

## 6. 采用该方案的原因

使用独立可执行程序而不是CTest，是为了不让长时间基准拖慢每次正确性回归。固定规模和固定价格模式便于重复运行，checksum和最终状态检查可以防止编译器或代码变更把核心操作优化掉，或出现悄无声息的拒单。

使用 `steady_clock` 适合测量经过时间；把准备和校验排除在计时区间外，可以分别观察目标操作。提交、撤单和撮合单独报告，避免一个综合数字掩盖具体瓶颈。

## 7. 可选替代方案

可以使用Google Benchmark获得统计分布、预热和重复迭代，但会引入额外依赖；第一版先使用C++标准库满足可移植性。可以增加Release、不同编译器、不同订单分布和多档位跨档负载，但必须分别标注，不能和Debug或单档位结果混表。

也可以使用Linux `perf`、Windows ETW或硬件计数器分析缓存和分支，但这些属于后续性能分析，不作为本阶段基础吞吐证据。多线程基准暂不加入，因为生产代码仍是单线程设计。

## 8. 性能瓶颈和后续优化方向

当前潜在瓶颈包括：`std::list`节点分配和缓存局部性、订单历史与提交账本的哈希访问、市场深度/价档累计量扫描、撮合时生成对侧价档和订单ID快照、成交历史 `vector` 扩容，以及Debug构建本身的额外开销。

基准数字只能说明固定负载下的端到端表现，不能单独证明某个容器是瓶颈。后续应先使用Release和采样工具确认，再考虑缓存价档累计量、减少全侧快照、改进内存分配或设计稳定节点结构。任何优化都必须重新运行第七阶段回归和数量守恒测试。

## 9. 常见技术追问与回答思路

**为什么不只报一个总耗时？**

提交、撤单和撮合访问的数据结构不同。分开测量更容易定位价格树、FIFO队列、索引和成交记录的影响。

**为什么撤单要把建簿放在计时区间外？**

目标是测量撤单操作本身。建簿是准备成本，混入后会让撤单数字随规模和初始化策略变化。

**为什么不能把Debug结果当作生产吞吐？**

Debug会影响优化、检查和代码生成。结果必须注明编译器、构建类型、硬件、负载和计时边界；Release结果也只能代表对应环境。

**为什么撮合负载不先堆积十万张被动单？**

当前撮合入口会生成对侧价格档和订单ID快照。先堆积后逐笔撮合会测到一个特定的累积深度成本，并可能形成平方级负载，不适合作为唯一通用指标。因此基础基准采用逐对成交，同时另行说明其边界。

**为什么不直接使用GoogleTest时间？**

正确性断言、参考模型和测试框架会改变被测路径。性能基准应独立运行，并保留状态校验以防止无效结果。
