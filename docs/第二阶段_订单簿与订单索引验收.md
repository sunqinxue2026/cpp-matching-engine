# 第二阶段：订单簿与订单索引验收

## 1. 本阶段目标

实现单标的订单簿与活动位置索引，验证价格顺序、同价FIFO、结构移除、空价格档清理和多容器一致性。负责人明确要求进入第二阶段，视为第一阶段闸门放行。本阶段完成后仍需负责人验收，不自动进入第三阶段。

订单簿是结构层。尚未提供订单提交服务、撮合、成交生成或业务撤单。结构移除不能被描述为订单已撤销。

## 3. 已实现的功能

- 单标的OrderBook，构造时验证标的格式。
- 买盘map按价格降序，卖盘map按价格升序，同价list保存OrderId。
- 活动unordered_map将ID映射为方向、价格、list节点迭代器。
- insert按ID读取外部OrderStore，拒绝未知ID、键值ID不一致、错误标的、活动重复、非活动状态、无剩余数量和非递增序号。
- 全簿成功入簿序号严格递增，失败不推进序号。同价队列按实际入簿顺序保持FIFO。
- erase先移除位置索引，再删除list节点，最后清理空价档；不存在返回false。
- contains、active_count、best_order、best_price、orders_at、levels只读查询。空最优价返回nullopt。
- levels返回独立快照，累计剩余数量采用溢出检查。
- check_invariants验证节点数、索引数、订单身份、标的、方向、价格、状态、剩余量和同价序列顺序。
- 禁止订单簿复制、移动及临时OrderStore绑定，避免复制位置索引或引用立即悬空。

重要：erase不修改Order状态、不删除历史，也不代表FILLED或CANCELED。当前Order没有状态转换接口，终态拒绝分支存在但尚不能通过正式接口构造终态测试。OrderStore全生命周期ID管理将在第三阶段实现。

## 5. 核心数据结构、算法和公式

```cpp
using OrderStore = std::unordered_map<OrderId, Order>;
using Queue = std::list<OrderId>;
using Bids = std::map<Price, Queue, std::greater<Price>>;
using Asks = std::map<Price, Queue>;
struct Location { Side side; Price price; Queue::iterator node; };
```

订单历史表唯一持有Order值。订单簿存ID而非另一份可变Order，防止剩余量或状态出现两个版本。当前历史表由调用方创建，须比OrderBook更晚销毁；第三阶段由OrderManager接管，期间不能删除、替换活动订单，也不能并发修改历史表。

入簿：查历史→校验→扫描该价档剩余量并检查溢出→创建档→尾插ID→建立位置索引→更新last_sequence。若尾插分配失败，删除本次新空档；若索引分配失败，删除本次节点及新空档，保留之前结构与序号。

移除：查位置→找对应档→删除位置索引→删除节点→清空档。没有对外泄露内部迭代器。

累计数量检查：对正数next，在相加前保证total <= INT64_MAX-next。避免先溢出再检查。

不变式检查对受控操作产生的结构进行核对，不是任意内存破坏检测器；已经悬空的迭代器不能靠这个函数安全修复。

## 6. 采用该方案的原因

Order用class封装；BookLevel用struct输出数据。价格树提供有序遍历，list允许任意节点位置删除且其余节点迭代器稳定，哈希表提供平均常数ID定位。

标准容器通过RAII回收节点，无裸new/delete、无共享所有权需要，不为展示技术加入shared_ptr。构造函数以std::move接管symbol，OrderStore使用const引用避免复制历史；查询const，返回值快照不允许调用方破坏内部结构。

unordered_map扩容会使其迭代器失效，本实现从不持久保存历史表或位置表的迭代器；保存的是list迭代器。外部历史表重哈希不会移动订单簿list节点。

全局序号严格递增是当前结构接口的前置契约。未来剩余订单应在当次提交处理完成时入簿；不得将旧序号订单在更晚序号入簿后重新插入。改单和恢复优先级不属于首版范围。

## 7. 可选替代方案

| 方案 | 优势 | 代价 |
|---|---|---|
| deque档位 | 队首尾操作方便、分配更集中 | 任意撤单和迭代器失效规则更复杂 |
| vector档位 | 连续内存、遍历快 | 中间删除移动元素，位置索引需更新 |
| 堆维护最佳价 | 取最优价方便 | 任意取消与完整深度遍历困难 |
| 档位缓存累计量 | 入簿不必扫描同档 | 后续成交扣量和移除必须同步更新累计量 |
| 侵入式链表/池化 | 可能降低分配与缓存成本 | 生命周期、回滚、指针安全更复杂 |
| 直接复制Order到簿 | 局部访问直观 | 历史与活动簿产生双重可变状态 |

第一版选择容易核验的结构，优化依据留待基准测试。

## 8. 性能瓶颈和后续优化方向

设价档L、活动单N、历史单H，单档订单数n_p：

- 入簿：平均O(log L+n_p)，因为防累计数量溢出需要扫描同档；哈希最坏仍可能线性。
- 移除：平均O(1)查ID+O(log L)找档+O(1)删节点。
- 最优订单：树begin及队首O(1)；最优价格另查历史表平均O(1)。
- 单档ID快照：O(log L+n_p)；完整深度O(N+L)，输出O(L)。
- 不变式检查：平均O(N+L)，大量测试逐单检查整体可能二次增长，不代表生产提交耗时。
- 空间：历史O(H)，活动ID、位置及档位O(N+L)，查询快照额外占用输出空间。

瓶颈包括list节点分配与缓存局部性、历史无限增长、哈希扩容和入簿重复扫描。未来缓存档位数量、reserve和历史留存策略都要与成交/撤单一致性共同设计。没有实测吞吐和时延，不提供性能数字。

## 9. 面试官可能追问的问题及回答思路

**为什么买降卖升？** 两侧begin都对应本侧最优报价，后续撮合直接检查对侧begin，无需每次遍历找最高或最低。

**同价为何FIFO？** 价格无法区分时，以引擎接收序号决定先后。insert在队尾，best_order取队首；不依赖墙上时钟的精度或回拨。

**为何不用unordered_map存价格？** 它不保证排序，无法自然产生价格优先；适合ID索引而非价档排序。

**为什么存ID，不存Order副本？** 全部状态只在历史表维护，避免成交更新一份却遗漏另一份。

**怎样防止悬空索引？** 禁止默认复制移动，位置索引先删，再删list节点。不能删除仍活跃的外部订单；所有权由第三阶段进一步封装。

**为什么erase没有CANCELED？** 它是结构操作，完成撮合也需要移除，因此不能一律撤销。业务撤单要在第六阶段协调历史状态和结构操作。

**异常安全怎么做？** 验证在变更前完成；两个分配点失败时回滚新节点/空档，成功后才推进序号。尚未注入bad_alloc，不能宣称已实测所有分配失败路径。

**为什么插入不是O(log L)？** 当前为保证单档数量不超int64上限扫描已有档内订单，增加O(n_p)。缓存累计量可优化，但会增加状态同步要求。

**部分成交后队列会怎样？** 后续在历史表更新剩余量，仍未完成的被动单留原节点，不重新排队；全部成交才移除。当前状态流转尚未实现。
